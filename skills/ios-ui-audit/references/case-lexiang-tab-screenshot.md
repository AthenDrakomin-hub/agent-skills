# 实战案例：乐享 IM tab 截图排查工作流

> **项目特定案例说明**：本文件绑定「乐享 IM」（boxim）这一具体项目的历史排查背景。其他项目不要直接套用其结论，仅复用其中的**五步排查方法**（读图定性 → 按规则定位 → 给修复 → 出报告 → 真机回归）。通用规则一律回到 `audit-h5-source.md` 的 H-* 编号清单。

用户贴出乐享 IM 的 tab 截图时，按本流程做实战排查，而不是只给通用清单。

## 项目背景（已知事实）

- 项目：乐享 IM，UniApp H5 打包进 iOS WKWebView 的套壳应用。
- 已报告症状：底部 tab 文字镜像翻转（来源：用户此前提供的截图与描述）。
- 环境特征：H5 套 iOS 壳，tab 栏为 H5 渲染而非原生 UITabBar。

## 截图排查工作流（五步）

### 第 1 步 · 读图定性
用图像读取能力仔细看截图，逐项记录：
- 哪些元素翻转：只有文字？还是文字+图标都翻转？只有某个 tab 还是全部？
- 翻转方向：水平镜像（scaleX）还是整段布局反向（RTL）？
- 伴随症状：tab 顺序是否也反了、图标是否错位、是否有底部遮挡/留白。

症状映射：
- 仅文字水平镜像、布局顺序正常 → 嫌疑 `transform: scaleX(-1)` 误用/渲染异常
- 文字镜像 + tab 排列顺序也反了 → 嫌疑 `dir="rtl"` 整体触发
- 图标正常、文字镜像 → 字体渲染层面问题（RTL 或 text-size-adjust）

### 第 2 步 · 按嫌疑定位（对照 audit-h5-source.md 清单）
1. RTL：让用户/自查 `<html dir>`、系统语言设置、CSS `direction` 残留（H-RTL-001，可跑 source_scan.py）
2. 镜像代码：全局搜索 `scaleX(-1)` / `scale(-1, 1)`
3. 若伴随缩放/遮挡：顺带查 viewport（H-VIEWPORT-001）与 safe-area（H-SAFE-001/002）

### 第 3 步 · 给出修复
- RTL 根因 → `<html lang="zh-CN" dir="ltr">`，移除动态改写 direction 的逻辑
- 镜像代码根因 → 删除或修正该 transform，确认 WKWebView 下渲染正常
- 修复代码必须可直接落地（HTML meta / CSS / 原生配置三选一给全）

### 第 4 步 · 输出诊断报告
按 `rubric.md` §7 的标注式模板输出（单案例可简化为四段式）：
```
【症状】截图所见：…
【根因判断】… （规则号 + 置信度：高/中/低，说明依据）
【修复方案】… （完整可落地代码）
【验证方式】真机 WKWebView 回归：检查 tab 文字方向、tab 排列顺序、点击切换后状态
```

### 第 5 步 · 回归验证清单
修复后在真机（非模拟器）确认：tab 文字方向正常、tab 顺序未反、切换 tab 后选中态正常、无新增底部遮挡。

## 注意事项

- 截图只能提供症状证据，根因结论要标注置信度；无法从截图确认的（如 HTML 源码里的 dir 属性），明确写「需查代码确认」并给出查什么。
- 本案例背景中的症状描述来自用户口述，若新截图症状与此不符，以新截图为准重新走第 1 步。
